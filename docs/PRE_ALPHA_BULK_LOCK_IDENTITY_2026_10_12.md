# Same-value bulk preview locks — 12 October 2026

Status: **candidate implementation detail** under Master v79 §9.7; not a new attribute model or sporting rule.

The existing first-season preview supports only the nine legacy 1–99 source fields. A Set Value & Lock operation changes two independent things: a player's observed numeric value and whether the field has an authenticated preview lock. A field with the target number and no lock needs a **new lock**, not a no-op. A field with that same number and an existing identical lock is a true no-op. Differently valued fields get both the target number and a lock. This means `unchangedCount` counts only players whose observed value *and* requested lock already match. An existing selected lock with a different target is replaced, while all unrelated locks remain.

The local display-only plan records `before/after` numeric value and `beforeLocked/afterLocked`; Automatic removes only selected field locks and leaves resulting numeric values **unknown** until the server has replayed the request. The explicit pending lock set, not the preview row objects, goes to the production server. Nothing in Stage or plan calculation updates the Run, Saved Revision, branch, Package, or real players. Verified preview and fingerprint gating remain mandatory before Adopt and manual Save. A successful bulk verification has exactly one session Undo to the preceding exact verified preview; it is not a persisted rollback.

Test expectations: mixed already-locked/new-same-value/numeric-different selections; exact no-op; unrelated locks preserved; immutability; duplicated or missing identities fail closed; backend preview and session Undo; Keep and saved proposal use the same authenticated reviewed player/lock input. A mock-backed UI test proves client interactions only, not production browser/restart acceptance. Any actual preview regression still requires server verification. No canonical 57-field or in-season general generation claim.
